## 1. ЧТО ЭТО ЗА ПРОДУКТ

Приложение (веб + бэкенд, возможно с локальным воркером для тяжёлого видео-рендеринга), которое:

1. **Забирает контент** из источников. Для MVP источник только один: видео, вручную загруженное пользователем. Новые источники не добавлять без отдельного решения Director.
2. **AI-модуль находит лучшие моменты** для клипов внутри длинного видео (по звуку, речи, эмоциям, всплескам активности чата/аудио, визуальным сценам).
3. **Авто-генерирует текст**: заголовки, описания, хэштеги, субтитры/капшены под каждый клип, адаптированные под целевые платформы MVP: YouTube и TikTok.
4. **Добавляет эффекты**: обрезка под вертикальный формат, субтитры со стилем, переходы, звуковые акценты, брендинг/watermark.
5. **Публикует автоматически** на привязанные аккаунты в соцсетях по расписанию или сразу.
6. **Учится на статистике**: собирает метрики (просмотры, лайки, retention, CTR) по каждому опубликованному клипу и **ищет паттерны**, какие моменты/форматы/заголовки дают больше просмотров — и постепенно улучшает выбор моментов и текстов.
7. **Дашборд**: список привязанных аккаунтов, статистика по каждому видео/клипу, сколько выложено, тренды эффективности, статус очереди публикаций.

> Текущие решения: целевые платформы MVP — YouTube и TikTok; продукт рассчитан на одного пользователя; бюджет MVP — 0.

## 2. ИЕРАРХИЯ АГЕНТОВ (для экономии токенов и лимитов)

Идея: не гонять одну "толстую" сессию через весь проект, а раскладывать работу по ролям с ограниченным контекстом на каждую. Если Codex/твоя среда поддерживает суб-агентов (sub-agents/tasks) — используй именно такое разделение. Если нет — эмулируй его дисциплиной: работай по одной роли за раз и не смешивай контексты.

### 2.1 DIRECTOR (Директор) — 1 экземпляр, минимальный контекст
- Держит в контексте только: `PROGRESS.md`, `ARCHITECTURE.md`, текущий roadmap/этап.
- Не читает код модулей напрямую.
- Разбивает большую задачу пользователя на 3-7 задач для MANAGER'ов.
- Принимает финальный отчёт от каждого MANAGER'а (кратко, 3-5 строк) и решает, что дальше.
- Никогда не пишет код сам.

### 2.2 MANAGER (Менеджер модуля) — по одному на каждый крупный модуль
Модули (см. раздел 3): `ingestion`, `ai_clipping`, `text_gen`, `video_effects`, `publisher`, `analytics_learning`, `dashboard`, `infra`.

- Контекст MANAGER'а ограничен ТОЛЬКО файлами своего модуля + интерфейсами (contracts) на стыке с другими модулями.
- Получает задачу от DIRECTOR, разбивает на конкретные тикеты для WORKER'ов.
- Ревьюит результат WORKER'а по факту (диффы, тесты), не переписывает всё заново.
- Отчитывается DIRECTOR'у кратко.

### 2.3 WORKER (Исполнитель) — временный, под конкретный тикет
- Получает ТОЛЬКО: конкретный тикет + список файлов, которые можно трогать + контракт (входы/выходы функции или API).
- Не имеет доступа к остальной кодовой базе, если это не нужно для тикета.
- Пишет код + минимальный тест + 1 строку в `PROGRESS.md`.
- Не занимается архитектурными решениями — если нужно решение, эскалирует MANAGER'у.

### 2.4 Правило экономии токенов
- Между агентами передавай **только выжимки**, а не полный контекст (сжатые интерфейсы/контракты вместо целых файлов).
- Явно фиксируй контракты между модулями в `CONTRACTS.md` (входы/выходы, форматы JSON, названия функций) — это позволяет MANAGER'ам и WORKER'ам не читать чужой код, а полагаться на контракт.
- Любая задача крупнее "написать один файл/функцию" должна сперва получить контракт, и только потом — реализацию.

## 3. МОДУЛИ СИСТЕМЫ (техническое ТЗ)

### 3.1 `ingestion` — Приём и подготовка контента
- Загрузка видео (файл / ссылка / стрим).
- Извлечение аудиодорожки, транскрипция речи (Whisper или аналог).
- Нарезка на сцены (scene detection) как предварительный слой перед AI-подбором моментов.

### 3.2 `ai_clipping` — Поиск лучших моментов
- Вход: транскрипт + таймкоды сцен + (опционально) аудио-эмоции/громкость/темп речи.
- Модель ранжирует сегменты по вероятной "виральности" — эвристики на старте (пики громкости, смех, ключевые фразы, темп), затем модель, дообучаемая на реальной статистике (см. 3.6).
- Выход: список кандидатов-клипов с таймкодами и confidence score.

### 3.3 `text_gen` — Тексты
- Заголовки, описания, хэштеги, субтитры под стиль платформы.
- Генерировать тексты на будущих этапах через выбранный LLM-подход. Не проектировать обязательную зависимость от платного API без явного одобрения; локальные модели и бесплатные tiers предпочтительнее там, где это разумно.

### 3.4 `video_effects` — Монтаж
- Кроп под вертикальный формат (9:16), автослежение за лицом/объектом в кадре (опционально).
- Наложение субтитров (стилизация), переходы, brand watermark, нормализация громкости.
- Рендер через ffmpeg (или аналог) — учитывай, что это самая тяжёлая по CPU/GPU часть, должна идти отдельным воркер-процессом/очередью, не блокируя основной бэкенд.

### 3.5 `publisher` — Автопостинг
- Интеграции с API соцсетей (у каждой платформы свои лимиты, форматы, OAuth) — уточни, какие платформы дают официальный API для автопостинга (у части платформ это ограничено/требует бизнес-аккаунт).
- Очередь публикаций с расписанием, ретраи при ошибках, лимиты частоты (rate limits соцсетей).
- Хранение токенов доступа аккаунтов — **обязательно шифрование в базе**, не хранить в открытом виде.

### 3.6 `analytics_learning` — Сбор статистики и обучение на паттернах
- Периодический сбор метрик по каждому опубликованному клипу (просмотры, лайки, комментарии, retention, если платформа отдаёт такие данные).
- Связка "фичи клипа" (длина, момент в исходном видео, тип текста/заголовка, наличие определённых слов, темп) → "результат" (просмотры/вовлечённость).
- Простая модель ранжирования (даже градиентный бустинг на табличных фичах — это дешевле и прозрачнее, чем сложная нейросеть) для приоритизации будущих кандидатов из `ai-clipping`.
- Важно: закладывай это ОТДЕЛЬНЫМ этапом после MVP — самообучение не нужно для первой рабочей версии, иначе распылишь ресурсы.

### 3.7 `dashboard` — Интерфейс
- Список аккаунтов (привязка/отвязка, статус токена).
- Список видео/клипов со статусами (в очереди, опубликовано, ошибка) и метриками.
- Общая статистика: сколько выложено за период, какие клипы/аккаунты лучше всего работают.
- Настройки стилей субтитров, шаблонов текста, расписания публикаций.

### 3.8 `infra`
- Очереди задач (например Redis/queue) для тяжёлых операций (транскрипция, рендер, публикация).
- Хранилище видео (S3-совместимое или локальное — уточни бюджет/масштаб).
- База данных: аккаунты, видео, клипы, метрики, логи публикаций.

### 3.9 Canonical repository structure and naming

```
backend/
  app/
    ingestion/
    ai_clipping/
    text_gen/
    video_effects/
    publisher/
    analytics_learning/
```

Все backend Python-модули находятся внутри `backend/app/`.
В архитектурных описаниях допустимы названия `ai-clipping`, `text-gen`, `video-effects`, `analytics-learning`.
Реальные Python package/directory names всегда: `ai_clipping`, `text_gen`, `video_effects`, `analytics_learning`.

## 4. ЭТАПЫ РАЗРАБОТКИ (roadmap)

Не проси Codex делать всё сразу — веди по этапам, каждый — отдельная "сессия работы" DIRECTOR'а:

1. **Этап 0 — Скелет**: репозиторий, структура папок по модулям, `PROGRESS.md`, `ARCHITECTURE.md`, `CONTRACTS.md`, базовая БД-схема.
2. **Этап 1 — MVP без AI**: manual video upload → Video → manual clip timestamps → Clip → video-effects → RenderedAsset → manual publishing to one platform → Publication. Stage 1 не зависит от `ai_clipping` и `text_gen`; AI clipping и text generation подключаются на следующих стадиях. Цель — сквозной pipeline работает.
3. **Этап 2 — Автотекст**: генерация заголовков/субтитров через LLM.
4. **Этап 3 — AI-подбор моментов (эвристики)**: без обучения, просто эвристики (громкость/пики/ключевые слова).
5. **Этап 4 — Дашборд**: аккаунты, статусы, базовая статистика.
6. **Этап 5 — Автопостинг по расписанию + очередь**.
7. **Этап 6 — Сбор метрик с платформ**.
8. **Этап 7 — Обучение на паттернах** (замена эвристик на модель, дообучаемую на реальных данных).

На каждом этапе DIRECTOR фиксирует в `PROGRESS.md` факт завершения и критерии приёмки.

## 5. ТЕХНОЛОГИЧЕСКИЙ СТЕК
- Бэкенд: Python 3.11+, FastAPI.
- Очереди: Redis + Celery.
- Видео: ffmpeg.
- Транскрипция: `faster-whisper` локально, с CPU fallback.
- LLM для текста/аналитики: будущий выбор; не делать платный API обязательной зависимостью без явного одобрения.
- БД: PostgreSQL.
- Фронтенд дашборда: React + Tailwind.
- Хранилище видео: S3-совместимое (MinIO локально / облако в проде).

## 6. ПРАВИЛА КАЧЕСТВА
- Каждый модуль — с минимальными unit-тестами на ключевую логику (особенно `ai_clipping` и `analytics_learning`).
- Секреты (API-ключи, токены соцсетей) — только через env/секрет-менеджер, никогда в коде.
- Rate limits соцсетей — закладывай retry+backoff с самого начала `publisher`, а не потом.
- Логи публикаций и ошибок — отдельная таблица, видна в дашборде.
