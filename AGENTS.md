# AGENTS.md — AI Clipper & Auto-Publisher

Этот файл читается Codex автоматически при старте сессии в этом репозитории. Не дублируй его содержимое в чат целиком без необходимости — обращайся к разделам по номеру.

## 0. Стек и окружение

- Бэкенд: Python 3.11+, FastAPI, SQLAlchemy + Alembic (миграции)
- Очередь задач: Redis + Celery (тяжёлые операции — транскрипция, рендер видео)
- БД: PostgreSQL
- Хранилище видео: S3-совместимое (MinIO локально / облако в проде)
- Фронтенд дашборда: React + Tailwind, отдельная папка `frontend/`
- Системный бинарник: `ffmpeg`
- Python-зависимости: `faster-whisper`, `yt-dlp`
- Песочница: `network_access = true` должен быть включён в `~/.codex/config.toml` под `[sandbox_workspace_write]` — иначе `pip install`/`npm install` зависают

> Если стек изменится — обнови этот раздел первым, до любых других правок.

## 2. Обязательные файлы-состояния (веди их всегда)

- **`PROGRESS.md`** — единственная долгосрочная память между сессиями. Одна строка на значимый шаг: дата, что сделано, что дальше. Без объяснений и кода внутри.
- **`ARCHITECTURE.md`** — обновляется только при изменении структуры модулей, не при каждом коммите.
- **`CONTRACTS.md`** — интерфейсы между модулями (входы/выходы функций, формат JSON, названия эндпоинтов). Любая межмодульная задача сначала получает контракт здесь, потом реализацию.

`PROGRESS.md` обновляется только после завершения значимого шага, при обнаружении существенного блокера или при изменении текущего Stage.
Не добавляй записи о каждом мелком действии и не записывай намерения перед началом работы.

## 3. Иерархия агентов

### Director
Director читает:
- `PROGRESS.md`
- `ARCHITECTURE.md`
- `CONTRACTS.md` при необходимости межмодульного решения
- текущий этап roadmap

Director не пишет production-код.

### Manager (по модулю)
Модули: `ingestion`, `ai_clipping`, `text_gen`, `video_effects`, `publisher`, `analytics_learning`, `dashboard`, `infra`.
Контекст ограничен файлами своего модуля + записями в `CONTRACTS.md`, касающимися стыков с другими модулями. Разбивает задачу на тикеты для Worker'ов, ревьюит по диффам и тестам.

### Worker
- пишет код;
- добавляет/обновляет минимальные тесты;
- возвращает Manager'у краткий отчёт: что изменено, какие тесты запущены, результат.

`PROGRESS.md` обновляет Manager после принятия работы Worker'а.

## 4. Модули

| Модуль | Назначение |
|---|---|
| `ingestion` | Приём видео, извлечение аудио, транскрипция (faster-whisper), scene detection |
| `ai_clipping` | Поиск лучших моментов: эвристики (громкость/темп/ключевые слова) → позже модель на реальных метриках |
| `text_gen` | Заголовки, описания, хэштеги, субтитры через LLM API |
| `video_effects` | Кроп 9:16, субтитры, переходы, watermark, рендер через ffmpeg |
| `publisher` | Интеграции с API соцсетей, очередь публикаций, retry/backoff, шифрование токенов аккаунтов |
| `analytics_learning` | Сбор метрик по клипам, поиск паттернов "фичи клипа → результат" |
| `dashboard` | React-интерфейс: аккаунты, статусы клипов, статистика |
| `infra` | Redis/Celery, S3-хранилище, схема БД |
## Границы модулей

Код backend-модулей находится в `backend/app/<module>/`.

Каноническая структура backend:

```
backend/
  app/
    ingestion/
    ai_clipping/
    text_gen/
    video_effects/
    publisher/
    analytics_learning/
    infra/
    main.py
  tests/
```

В архитектурных описаниях допустимы человекочитаемые названия `ai-clipping`, `text-gen`, `video-effects`, `analytics-learning`.
Реальные Python package/directory names всегда используют snake_case: `ai_clipping`, `text_gen`, `video_effects`, `analytics_learning`.

Тесты:
`backend/tests/<module>/`.

Frontend:
`frontend/`.

Локальные видео и промежуточные файлы:
`storage/` — никогда не коммитить.

## 5. Правила качества и безопасности

- Секреты (API-ключи, токены соцсетей) — только через `.env`/секрет-менеджер, никогда в коде и никогда не печатать их в чат/логи.
- Токены доступа аккаунтов в БД — только в зашифрованном виде.
- Rate limits соцсетей — retry+backoff закладывать в `publisher` сразу, не постфактум.
- Каждый модуль — минимальные unit-тесты на ключевую логику, особенно `ai_clipping` и `analytics_learning`.
- Диффы, а не пересоздание файлов целиком, если файл больше ~100 строк.
- Не печатать в чат содержимое непотронутых файлов без необходимости.

## 6. Этапы разработки (текущий этап отмечай в PROGRESS.md)

0. Скелет: структура папок, `PROGRESS.md`, `ARCHITECTURE.md`, `CONTRACTS.md`, базовая схема БД
1. MVP без AI: manual video upload → Video → manual clip timestamps → Clip → `video_effects` → RenderedAsset → manual publishing to one platform → Publication. Этап 1 не зависит от `ai_clipping` и `text_gen`; они подключаются на следующих стадиях.
2. Автотекст (заголовки/субтитры через LLM)
3. AI-подбор моментов на эвристиках (без обучения)
4. Дашборд: аккаунты, статусы, базовая статистика
5. Автопостинг по расписанию + очередь
6. Сбор метрик с платформ
7. Обучение на паттернах (замена эвристик моделью)

Не переходи к следующему этапу, пока предыдущий не отмечен завершённым в `PROGRESS.md`.

## 7. Ограничения проекта

### Пользователь
- MVP рассчитан на одного пользователя.
- Исходные видео загружает пользователь вручную.

### Локальные вычисления
- Машина разработчика: NVIDIA RTX 3070 8 GB VRAM, 32 GB RAM.
- Для транскрипции предпочитай локальный `faster_whisper`.
- Не выбирай автоматически самые тяжёлые модели.
- Предпочитай конфигурации, которые стабильно помещаются в 8 GB VRAM.
- CPU fallback должен оставаться возможным.

### Ограничение бюджета
Бюджет MVP: 0.

Поэтому:
- предпочитай open-source и локальные решения;
- не добавляй платный SaaS без явного одобрения;
- не проектируй обязательную зависимость от платного LLM/API;
- локальные модели и бесплатные tiers предпочтительнее там, где это разумно.

### Автономность
Приложение должно поддерживать автономное выполнение задания:

пользователь создаёт задачу → система обрабатывает её без постоянного участия пользователя → пользователь позже проверяет результат.

Долгие операции должны:
- выполняться через очередь;
- сохранять статус;
- переживать перезапуск backend;
- сохранять ошибки для последующего просмотра;
- поддерживать безопасный retry там, где операция идемпотентна.

Перед любым значимым изменением:

1. Прочитай `PROGRESS.md`.

3. Осмотри структуру проекта и существующие файлы нужного модуля.
4. Не создавай файл, если эквивалентный файл уже существует.
